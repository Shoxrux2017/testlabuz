# 2. Database Design Principles

## 2.1 UUID Primary Keys

### Database design choice

Domain tables should use PostgreSQL `uuid` primary keys.

Example:

```text
id uuid primary key
```

UUIDs should be generated by the backend or PostgreSQL using one consistent project convention.

Reasons:

- Safe identifiers across desktop/mobile/API boundaries
- Easier data generation across environments
- No security dependence on sequential IDs
- Compatible with shared-schema institution data

Authorization must still protect every record. UUIDs are **not** a replacement for authorization.

---

## 2.2 Timestamps and Timezone Storage

Use PostgreSQL:

```text
timestamptz
```

for authoritative stored instants such as:

- `created_at`
- `updated_at`
- `activated_at`
- `started_at`
- `deadline_at`
- `submitted_at`
- `finalized_at`
- `checked_at`
- `calculated_at`
- `closed_at`

All authoritative instants are stored as UTC-equivalent PostgreSQL `timestamptz` values.

Each institution has one configured IANA timezone in `institution_settings.timezone`, for example:

```text
Asia/Tashkent
```

Teacher-entered educational dates/times are interpreted using the institution timezone and converted to authoritative instants before persistence.

Changing the institution timezone must not rewrite already-stored absolute timestamps. Device clock and device timezone are never authoritative for deadlines or Blitz timing.

---

## 2.3 No Generic Global Status Column

Do not use one status enum for unrelated concepts.

Separate:

- Institution status
- User status
- Group status
- Topic lifecycle
- Homework lifecycle
- Blitz lifecycle
- Attempt/submission status
- Checking status
- Result calculation status
- Result visibility

---

## 2.4 Prefer `varchar + CHECK` for Business Enums

### Database design choice

Use constrained `varchar` columns rather than PostgreSQL native enum types for most business statuses.

Example:

```text
status varchar(32) not null
check (status in ('draft', 'active', 'closed', 'archived'))
```

Reasons:

- Easier Laravel migrations
- Easier controlled evolution
- Still provides database validation
- Avoids difficult native-enum alteration workflows

Laravel application enums should mirror these database values.

---

## 2.5 Direct Institution Ownership on High-Risk Tables

The following tables should store `institution_id` directly:

- `users`
- `groups`
- relationship tables
- `topics`
- `files`
- `learning_materials`
- `assessments`
- `assessment_students`
- `questions`
- `assessment_attempts`
- `attempt_answers`
- `official_task_scores`
- `blitz_attempt_exceptions`
- `topic_result_pairs`
- `topic_results`

This is intentional redundancy for safe query scoping and constraint enforcement.

---

## 2.6 Database Constraints + Application Rules

Database constraints should enforce structural integrity.

Application/domain services enforce context-sensitive business rules.

Example:

Database can enforce:

```text
attempt_number > 0
score between 0 and 100
unique attempt number per student/task
foreign-key existence
```

Application must enforce:

```text
Teacher is assigned to group
Student is eligible for task
Blitz is currently active
Deadline has not passed
```

---

## 2.7 Historical Data Is Preserved

Do not hard-delete records that already participate in:

- Attempts
- Submissions
- Scores
- Results
- Historical relationships

Prefer lifecycle fields such as:

- `is_active`
- `status`
- `ended_at`
- `closed_at`
- `archived_at`
- `removed_at`

---

## 2.8 No Large File Bytes in Domain Tables

Store file metadata in PostgreSQL.

Store file bytes in private Laravel-managed storage.

# 3. Multi-Institution / Tenant Model

## 3.1 Tenant Root

The tenant root is:

```text
institutions
```

Every institution-level record must resolve to one institution.

---

## 3.2 Platform-Level Exception

A Platform Owner / Super Admin user is platform-scoped and may have:

```text
institution_id = null
```

All other MVP roles must belong to exactly one institution.

---

## 3.3 Required Institution Check Pattern

For institution-owned records:

```text
authenticated_user.institution_id
==
requested_record.institution_id
```

must be true before institution-level authorization continues.

---

## 3.4 Cross-Institution Foreign-Key Integrity

Where feasible, use composite uniqueness/foreign-key patterns or application checks so relationships cannot connect different institutions.

Examples:

```text
Teacher A (Institution 1)
must not join
Group B (Institution 2)
```

```text
Parent A (Institution 1)
must not connect
Student B (Institution 2)
```

Application validation remains mandatory even when a structural database constraint exists.

# 8. Institution Settings

## 8.1 Table: `institution_settings`

Purpose:

Stores one current business-setting row per institution.

### Columns

| Column | Type | Null | Notes |
|---|---|---:|---|
| `institution_id` | uuid | no | PK + FK |
| `acceptable_score_difference` | numeric(12,8) | yes | Null until Institution Admin configures |
| `blitz_timer_start_mode` | varchar(24) | yes | Null until Institution Admin configures |
| `student_result_release_mode` | varchar(30) | yes | Null until Institution Admin configures |
| `parent_result_release_mode` | varchar(30) | yes | Null until Institution Admin configures |
| `timezone` | varchar(64) | no | IANA timezone, e.g. `Asia/Tashkent` |
| `learning_material_max_mb` | smallint | no | Institution limit, max 25 |
| `student_submission_max_mb` | smallint | no | Institution limit, max 15 |
| `updated_by_user_id` | uuid | yes | Null for system initialization; Institution Admin after explicit configuration |
| `created_at` | timestamptz | no | |
| `updated_at` | timestamptz | no | |

### Constraints

```text
acceptable_score_difference is null OR acceptable_score_difference between 0 and 100
```

```text
blitz_timer_start_mode is null OR blitz_timer_start_mode in ('synchronized', 'individual')
```

```text
student_result_release_mode is null OR student_result_release_mode in ('automatic', 'manual_teacher')
```

```text
parent_result_release_mode is null OR parent_result_release_mode in ('with_student', 'manual_teacher', 'hidden')
```

```text
learning_material_max_mb between 1 and 25
student_submission_max_mb between 1 and 15
```

`timezone` must be validated by the Laravel domain/application layer against the supported IANA timezone database. A simple non-empty database CHECK may also be used, but PostgreSQL should not attempt to reproduce the full IANA registry. New institutions are initialized with `timezone = 'Asia/Tashkent'`, `learning_material_max_mb = 25`, and `student_submission_max_mb = 15`.

`acceptable_score_difference`, `blitz_timer_start_mode`, `student_result_release_mode`, and `parent_result_release_mode` intentionally start as `NULL`. They have **no silent educational default**. Laravel checks required settings before dependent operations and returns an institution-settings conflict when a needed value is still null. General institution/user/group operations remain valid.

### Attempt Configuration Is Intentionally Absent

The MVP must **not** persist configurable Homework or Blitz attempt limits in institution settings.

The business rules are fixed:

```text
Homework normal attempts = 3
Blitz normal attempts = 1
Blitz additional exception attempts = at most 1 per Student/Blitz
```

These are domain invariants, not institution settings.

### Upload-Limit Rule

Platform hard maxima are:

```text
Learning material = 25 MB per file
Student submission = 15 MB per file
```

The institution fields may only reduce those maxima.

### Codes

```text

partially_understood
needs_revision
needs_teacher_support
not_completed
```

### Unique

```text

```

### Constraints

For numeric categories:

```text
min_score is not null
max_score is not null
0 <= min_score <= max_score <= 100
```

For:

```text

```

```text
min_score is null
max_score is null
```

### Cross-Row Validation

“No gaps / no overlaps / full 0–100 coverage” requires application/domain validation inside a transaction because ordinary row-level CHECK constraints cannot safely validate the complete category set.

Category resolution uses the persisted integer `topic_results.category_score`, derived from the unrounded final score using `.0`–`.5` down and `>.5` up; it does not use the one-decimal display value.

## 12.2 Timer-Start Mode Snapshot

## 12.3 Timeout Persistence

At the authoritative deadline, saved Blitz work is finalized automatically.

Persistence must support:

- Explicit Student submission before timeout.
- Server timeout finalization.
- Rejection of answer writes after `deadline_at`.
- Preservation of answers saved before timeout.
- Zero points for unanswered questions.
- Manual review for answered questions requiring Teacher judgment.

Timeout finalization is represented on `assessment_attempts` with:

```text
finalized_at
finalization_reason = 'timeout_auto_submit'
```

and an appropriate finalized/review status.

An automatically finalized timeout attempt is **not** treated as a missing unsubmitted attempt.

## 15.1 Table: `assessment_students`

Purpose:

### Database design decision — recipient snapshot

Recipient rows represent Students actually assigned the task. This prevents later Group-membership changes from silently rewriting the historical meaning of an already-active Homework or Blitz task.

### Population Behavior

For:

```text
assignment_mode = selected_students
```

### Homework Deadline Auto-Finalization Rule

Homework uses `homework_assignments.deadline_at` as the authoritative deadline; the Attempt-level `deadline_at` column remains reserved for effective Blitz deadlines. At Homework deadline reconciliation, every matching `in_progress` Homework Attempt is atomically finalized from saved answers. The transaction sets:

```text
finalized_at = authoritative Homework deadline/current reconciliation time
finalization_reason = 'homework_deadline_auto_submit'
locked_at = finalized_at
submitted_at = null
```

Unanswered components are persisted/evaluated as zero according to scoring rules, answered automatic components are checked, and answered manual-review components may move the Attempt to `waiting_for_teacher_review`; otherwise it may move directly to `checked`. No empty Attempt row is created for a Student who never started. After the Homework deadline, the remaining unused normal-attempt capacity is unavailable.

### Timeout Rule

For Blitz, `deadline_at` is set when the attempt starts:

- synchronized mode → task `synchronized_ends_at`
- individual mode → `started_at + duration_seconds`

The timeout finalization transaction sets:

```text
finalized_at = authoritative deadline/current reconciliation time
finalization_reason = 'timeout_auto_submit'
locked_at = finalized_at
```

and records the appropriate status based on whether Teacher review remains.

### Concurrency

Starting a new Attempt uses a transaction/lock or equivalent guard so concurrent requests cannot create duplicate next attempt numbers or bypass fixed attempt limits.

# 18. Automatic and Manual Scoring

Scoring is persisted at Question/Attempt levels.

No separate duplicated “auto score” table is required.

## 18.1 Question-Level Score

Stored in:

```text
attempt_answers.awarded_points
```

with:

```text
attempt_answers.checking_status
```

and Teacher review metadata where applicable.

---

## 18.2 Attempt-Level Score

Stored in:

```text
assessment_attempts.earned_points
assessment_attempts.possible_points
assessment_attempts.normalized_score
assessment_attempts.scoring_completed_at
```

### Score Readiness

If any required answer remains waiting for Teacher review, `assessment_attempts.normalized_score` remains null until complete scoring.

The normalized score is calculated from the complete awarded-point total and persisted with high internal precision. It must **not** be rounded to the one-decimal UI format before official-score selection, Homework–Blitz comparison, or threshold evaluation. Category assignment derives a separate integer `category_score` from the final internal score.

---

## 18.3 Approved Partial-Credit Rules

The database supports decimal awarded points; the application writes them according to these fixed policies.

### Single-choice

```text
full question points if correct
0 if incorrect
```

### True / false

```text
full question points if correct
0 if incorrect
```

### Multiple-choice

The maximum Student selection count is derived from the number of correct options. Laravel rejects an answer containing more selected options than that count. Awarded points use only correctly selected answers:

```text
ratio = correctly_selected_options / total_correct_options
awarded_points = question.points * ratio
```

An empty selection earns zero. Incorrectly selected options earn no credit and create no extra negative penalty. The selection cap prevents “select everything”.

### Matching

```text
ratio = correctly_matched_pairs / total_pairs
awarded_points = question.points * ratio
```

### Ordering

```text
ratio = correctly_positioned_items / total_items
awarded_points = question.points * ratio
```

### Fill-in-the-blank

```text
ratio = correctly_completed_blanks / total_blanks
awarded_points = question.points * ratio
```

### Short written answer

Automatic mode is all-or-nothing against accepted-answer rules after deterministic text normalization (Unicode NFC normalization, trim, consecutive-whitespace collapse, Unicode case-fold comparison, common Uzbek apostrophe normalization; punctuation/technical symbols preserved). No fuzzy/AI matching is used. Manual mode allows Teacher-awarded points from 0 through the question maximum.

### Open written / file-based

Teacher assigns points from 0 through the question maximum.

No negative marking is introduced by these rules.

## 19.1 Table: `official_task_scores`

Purpose:

Stores the single official score source for one Student and one Assessment while preserving all Attempt history separately.

| Column | Type | Null | Notes |
|---|---|---:|---|
| `id` | uuid | no | PK |
| `institution_id` | uuid | no | |
| `assessment_id` | uuid | no | |
| `student_id` | uuid | no | |
| `official_attempt_id` | uuid | no | Fully scored eligible Attempt |
| `normalized_score` | numeric(12,8) | no | 0–100 snapshot |
| `selection_policy_code` | varchar(64) | no | Fixed policy snapshot |
| `selected_by_user_id` | uuid | yes | Usually null/system for deterministic resolution |
| `selected_at` | timestamptz | no | |
| `created_at` | timestamptz | no | |
| `updated_at` | timestamptz | no | |

### Unique

```text
unique(assessment_id, student_id)
```

### Constraints

```text
normalized_score between 0 and 100
```

```text
selection_policy_code in (
  'highest_valid_completed',
  'valid_normal_blitz',
  'approved_blitz_exception_replacement'
)
```

### Homework Official Score

For Homework, the resolver considers fully scored, valid, eligible attempts among numbers 1–3 and selects the highest `normalized_score`.

```text
selection_policy_code = 'highest_valid_completed'
```

If multiple attempts have the same highest normalized score, the attempt with the **lowest `attempt_number`** is selected as `official_attempt_id`. The numeric official score is unchanged.

### Blitz Official Score

Without exception:

```text
official_attempt_id = valid completed attempt #1
selection_policy_code = 'valid_normal_blitz'
```

With an approved exception:

- Attempt #1 has `official_score_eligible = false`.
- The valid fully scored replacement Attempt #2 becomes official.

```text
selection_policy_code = 'approved_blitz_exception_replacement'
```

The Teacher grants the exception but does **not** manually choose the official score.

### Integrity

`official_attempt_id` must reference an Attempt belonging to:

- The same Assessment.
- The same Student.
- The same institution.
- A fully scored Attempt.
- `official_score_eligible = true`.

Application/domain validation enforces this transactionally.

# 20. Topic Result Pair and Topic Results

## 20.1 Table: `topic_result_pairs`

Purpose:

Stores the Topic-level official result-bearing pair. The row is created when the official Homework is designated and is completed later when the official Blitz is available.

A Topic may contain multiple Homework and Blitz tasks, but the MVP uses exactly one designated **whole-group Homework** and exactly one designated **whole-group Blitz** to calculate Student Topic results. Selected-Student assessments are practice-only and cannot be designated.

### Columns

| Column | Type | Null | Notes |
|---|---|---:|---|
| `id` | uuid | no | PK |
| `institution_id` | uuid | no | |
| `topic_id` | uuid | no | Exactly one pair per Topic |
| `homework_assessment_id` | uuid | no | Must be Homework in same Topic |
| `blitz_assessment_id` | uuid | yes | Nullable until the official Blitz is designated; when present it must be a Blitz in the same Topic |
| `designated_by_user_id` | uuid | no | Authorized Teacher |
| `designated_at` | timestamptz | no | |
| `cohort_snapshotted_at` | timestamptz | yes | Nullable until the official cohort is established from the first activated official whole-group task; may be set while `blitz_assessment_id` is still null |
| `locked_at` | timestamptz | yes | May be set by the first relevant official Student Attempt even while `blitz_assessment_id` is null |
| `created_at` | timestamptz | no | |
| `updated_at` | timestamptz | no | |

### Unique

```text
unique(topic_id)
```

A result-bearing Assessment should not be reused as the official task for multiple unrelated Topics; the same-Topic relationship already follows from `assessments.topic_id`.

### Integrity

Application/domain validation must require:

```text
homework_assessment_id:
  required
  same institution/topic
  assessment.type = 'homework'
  assignment_mode = 'group'

blitz_assessment_id:
  nullable
  when non-null:
    same institution/topic
    assessment.type = 'blitz'
    assignment_mode = 'group'
    != homework_assessment_id

locked_at IS NOT NULL
  => cohort_snapshotted_at IS NOT NULL
```

### Cohort and Lock Rule

The Teacher must designate only whole-group assessments. The first activated official whole-group task establishes the common cohort from its persisted `assessment_students` snapshot and sets `cohort_snapshotted_at`. If an already-active eligible whole-group Homework is designated before any Student Attempt, its existing persisted Group recipient snapshot becomes the official cohort. If only that official Homework exists, the backend does not create a Blitz Assessment or Blitz recipient rows. When the official Blitz is later designated or activated, its recipient snapshot must use exactly the established cohort; a conflicting existing snapshot is rejected rather than silently rewritten. Once snapshotted, later Group membership changes do not rewrite the official cohort. Before `locked_at`, an authorized Teacher may replace the official Homework only when the backend eligibility rules allow it and no existing Student work is reinterpreted.

When the first relevant official Student Attempt begins, `locked_at` is set and the already-designated official task/cohort cannot be replaced or mutated. A valid staged row may have `homework_assessment_id`, `cohort_snapshotted_at`, and `locked_at` set while `blitz_assessment_id` remains null. Stage 8 may fill the null Blitz reference when the official-Blitz and cohort rules pass; this completes the pair and must not clear `locked_at`, replace the official Homework, or change the locked cohort.

### Score Precision Policy

When a numeric result is calculated:

```text
score_precision_policy_code = 'unrounded_internal_display_1_decimal_category_half_down'
```

The database stores high-precision internal values. One-decimal rounding is a presentation/API display concern and must not overwrite stored calculation values. `category_score` is derived separately: `.0`–`.5` rounds down and `>.5` rounds up, then inclusive integer category ranges are applied.

### Result Release Policy Snapshots

Release-policy settings are not required for numeric result calculation. If both applicable institution release modes are configured when the result is calculated, they may be snapshotted immediately. If either is still null, the corresponding `*_release_mode_used` remains null and release is blocked. Immediately before the first visibility decision after the Institution Admin completes configuration, the backend snapshots the then-current non-null release mode(s) and uses those snapshots thereafter.

Allowed non-null values:

```text
student_release_mode_used in ('automatic', 'manual_teacher')
parent_release_mode_used in ('with_student', 'manual_teacher', 'hidden')
```

This preserves why visibility behaved as it did even if institution settings later change.

### Visibility Constraint

A Parent must never see a result before the Student:

```text
parent_visible_at is null
OR
(
  student_visible_at is not null
  and parent_visible_at >= student_visible_at
)
```

### Score Constraints

For each non-null 0–100 score/range snapshot:

```text
value between 0 and 100
```

For `category_score`:

```text
category_score is null OR category_score between 0 and 100
```

`category_score` is an integer because its column type is `smallint`.

### Unique

One Student has one Topic result:

```text
unique(topic_id, student_id)
```

This is now a locked MVP constraint.

### Closure Preconditions

`result_status = closed` may be written only when the Student+Topic result is terminal: either `calculated` with both official scores, all manual review complete, and no relevant in-progress/pending replacement attempt; or definitive `not_completed` because required work can no longer validly be completed. Waiting states cannot transition to closed. Closure does not depend on Student/Parent visibility and does not require class-wide task closure.

### Historical Snapshot Rule

After `result_status = closed`:

- Do not recalculate silently.
- Do not replace rule snapshots.
- Do not change the designated result pair.
- Do not change official score references through ordinary MVP editing.
- Do not change numeric result data through release actions.

Visibility remains a separate controlled capability according to the approved release policy.

Result calculation and visibility are separate.

## 22.1 Approved Release Behavior

Institution policy lives in:

```text

```

Student modes:

```text
automatic
manual_teacher
```

Parent modes:

```text
with_student
manual_teacher
hidden
```

Rules:

- `automatic` Student mode sets `student_visible_at` after the result is fully calculated and all required checking is complete.
- `manual_teacher` Student mode leaves `student_visible_at = null` until an authorized Teacher releases it.
- `with_student` Parent mode sets Parent visibility when Student visibility begins.
- `manual_teacher` Parent mode requires a separate authorized Teacher release **after** Student visibility exists.
- `hidden` keeps `parent_visible_at = null`.
- Parent visibility must never precede Student visibility.
- Changing visibility must not change the result formula, scores, category, consistency, or calculation status.

The snapshots on `topic_results` preserve the release modes applicable to that result.

# 28. Security and Institution Data Isolation

## 28.1 Every High-Risk Query Starts With Tenant Scope

Example conceptual SQL:

```sql
select *
from topics
where institution_id = :authenticated_institution_id
  and id = :topic_id;
```

not:

```sql
select *
from topics
where id = :topic_id;
```

followed by assumptions.

---

## 28.2 Institution ID Is Server-Controlled

The backend should derive institution ownership from authenticated context and authorized parent records.

Do not accept a client `institution_id` as authoritative ownership for creates.

---

## 28.3 Role Integrity

Database CHECK constraints validate role values.

Application services validate that role matches relationship usage.

Examples:

- `teacher_id` must reference a Teacher.
- `student_id` must reference a Student.
- `parent_id` must reference a Parent.

A plain foreign key cannot enforce the referenced user's role; this requires application validation or optional database triggers.

For MVP portability and maintainability:

> Use application/domain validation plus automated tests rather than role-check triggers.

---

## 28.4 Composite Tenant Integrity

Where the implementation team judges the additional complexity worthwhile, high-risk relationships may add composite unique keys such as:

```text
unique(id, institution_id)
```

and composite foreign keys:

```text
(child_id, institution_id)
→
(parent.id, parent.institution_id)
```

This creates an additional database-level cross-tenant barrier.

### Recommended for MVP

Use this pattern at least for the highest-risk learning records if Laravel migration complexity remains manageable:

- Groups
- Topics
- Assessments
- Attempts
- Answers
- Results

If not used, mandatory transactional application validation and negative cross-institution tests remain required.

---

## 28.5 Row-Level Security

PostgreSQL Row-Level Security (RLS) is **not required** for the MVP baseline.

Authorization remains Laravel-controlled.

RLS may be evaluated later as defense-in-depth if operational complexity justifies it.

# 29. Resolved MVP Database Decision Contracts

All ten previously open decisions are resolved. The database contract is now:

## DEC-01 — Official Attempt Strategy

- Homework has 3 normal Attempts.
- `official_task_scores` selects the highest valid fully scored Homework Attempt.
- Blitz normally uses Attempt #1.
- When an approved exception exists, invalidated Attempt #1 is ineligible and valid replacement Attempt #2 becomes official.
- Teacher does not manually choose the official score.

---

## DEC-02 — Technical Attempt Exception

The MVP includes:

```text
blitz_attempt_exceptions
```

Exactly one exception may exist per Student/Blitz. It records the invalidated Attempt, required reason, Teacher actor, timestamp, and optional replacement Attempt reference.

---

## DEC-03 — Blitz Timer Start Mode

Institution setting:

```text
blitz_timer_start_mode in ('synchronized', 'individual')
```

Teacher configures:

```text
blitz_tasks.duration_seconds
```

Activation snapshots the mode to `blitz_tasks.timer_start_mode_snapshot`.

No per-question timer field exists.

---

## DEC-04 — Blitz Timeout Behavior

`assessment_attempts` stores:

```text
deadline_at
finalized_at
finalization_reason
```

Timeout finalization uses:

```text
finalization_reason = 'timeout_auto_submit'
```

Saved answers are finalized; unanswered questions receive zero; manual answers remain reviewable.

---

## DEC-05 — Partial Credit

No additional schema tables are required. Decimal awarded-point fields persist the approved scoring outcomes for multiple-choice, matching, ordering, fill-in-the-blank, and manual-scored questions.

---

## DEC-06 — Score Precision / Display Rounding

High-precision values are stored in numeric score fields. Topic comparison and final-score calculation use those internal values. Category assignment uses the separately persisted integer `category_score` derived with `.0`–`.5` down and `>.5` up.

`topic_results.score_precision_policy_code` records:

```text
unrounded_internal_display_1_decimal_category_half_down
```

The one-decimal display value is not persisted over the authoritative internal score.

---

## DEC-07 — Result Release

`institution_settings` stores nullable educational-policy values:

```text
student_result_release_mode
parent_result_release_mode
```

They begin null until Institution Admin configuration; release operations must reject missing required policy.

`topic_results` stores independent Student/Parent visibility timestamps, optional release actors, and release-policy snapshots.

---

## DEC-08 — Maximum Upload Sizes

Platform maxima:

```text
learning material = 25 MB
Student submission = 15 MB
```

`files.size_bytes` records actual size. `institution_settings` may store only lower/equal MB limits.

---

## DEC-09 — Timezone

All authoritative instants use PostgreSQL `timestamptz`.

`institution_settings.timezone` stores one IANA timezone per institution.

Changing the institution timezone never rewrites existing absolute timestamps.

---

## DEC-10 — Result-Bearing Pair

The MVP includes:

```text
topic_result_pairs
```

At most one row exists for each Topic. It first designates the whole-group official Homework and may keep a null Blitz reference until the whole-group official Blitz is added later. The first activated official task establishes the persisted `assessment_students` cohort, and the later official task must reuse it. Selected-Student tasks are practice-only. Relevant Student activity locks the existing official work/cohort but does not prevent one-time completion of the absent Blitz side.

`topic_results(topic_id, student_id)` is uniquely constrained.

---

## 29.11 Post-Audit Database Clarifications

- Administrator-created accounts persist `must_change_password = true` until authenticated password change clears it.
- Institution lifecycle idempotency and HTTP idempotency-key semantics are API/application concerns; no duplicate educational domain rows may be created.
- The first activated official whole-group task establishes the persisted official cohort; no missing official task or recipient rows are fabricated, and the later official task must use the same Student set.
- `finalization_reason` distinguishes `student_submit`, `timeout_auto_submit`, `task_closed_auto_finalize`, and `homework_deadline_auto_submit`.
- No schema supports Teacher-selected official Homework attempt; highest-score ties deterministically use the lowest attempt number.

# 31A. Homework Deadline Persistence Decision — Resolved

No new Attempt status is required solely for Homework deadline finalization. An in-progress Homework Attempt becomes immutable at the authoritative deadline, records `finalized_at`, `locked_at`, and `finalization_reason = 'homework_deadline_auto_submit'`, leaves `submitted_at = null`, and then uses the normal `checked` or `waiting_for_teacher_review` status according to scoring readiness. The official-score resolver may use the finalized Attempt once it is fully checked and otherwise eligible. Students who never started remain represented only by their recipient row; no empty Attempt is fabricated.
